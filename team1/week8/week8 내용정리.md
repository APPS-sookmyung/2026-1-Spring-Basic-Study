# Spring Basic Week 8 - Service, Repository와 DI 이해하기

이번 주는 **Spring MVC에서 Model 영역이 어떻게 구성되는지**, 그리고
**DI(의존성 주입)**가 왜 필요한지 학습했다.

------------------------------------------------------------------------

## Spring MVC의 흐름

Spring MVC에서는 각 계층이 맡은 역할이 명확하게 나뉜다.

``` text
Controller → Service → Repository → Database
```

### Controller

-   사용자의 요청을 받음
-   Service에 필요한 작업을 요청
-   결과를 사용자에게 반환

### Service

-   비즈니스 로직 처리
-   데이터를 가공하거나 필요한 연산 수행
-   Repository를 통해 데이터를 조회하거나 저장

### Repository

-   데이터베이스와 직접 통신
-   CRUD(조회, 저장, 수정, 삭제) 수행

즉, Controller는 요청을 전달하고, Service는 로직을 수행하며,
Repository는 데이터를 관리하는 역할을 한다.

------------------------------------------------------------------------

# DI(Dependency Injection)

DI는 필요한 객체를 직접 생성하지 않고 **스프링 컨테이너가 대신 주입해
주는 방식**이다.

기존 방식처럼 객체를 직접 생성하면

``` java
ProductService service = new ProductService();
```

객체 생성이 코드 곳곳에 퍼지게 되고 클래스 간 결합도가 높아진다.

DI를 사용하면 객체 생성은 스프링이 담당하고, 필요한 곳에서는 주입만 받아
사용하면 된다.

### DI를 사용하는 이유

-   객체 간 결합도를 낮출 수 있다.
-   코드 재사용이 쉬워진다.
-   테스트하기 편하다.

------------------------------------------------------------------------

# @Autowired

`@Autowired`는 스프링 빈(Bean)을 자동으로 찾아 주입해 주는
어노테이션이다.

직접 `new`를 사용하지 않아도 필요한 객체를 사용할 수 있다.

------------------------------------------------------------------------

# DI 방식 3가지

### 1. Setter 주입

``` java
@Autowired
public void setRepository(ProductRepository repository) {
    this.repository = repository;
}
```

-   수정이 가능해 안정성이 떨어짐

------------------------------------------------------------------------

### 2. 필드 주입

``` java
@Autowired
private ProductRepository repository;
```

-   코드가 간단함
-   테스트하기 어려움

------------------------------------------------------------------------

### 3. 생성자 주입 (권장)

``` java
@Autowired
public ProductService(ProductRepository repository) {
    this.repository = repository;
}
```

-   객체 생성 시 의존성이 함께 주입됨
-   불변성을 유지할 수 있음
-   테스트가 가장 쉬워 현재 가장 많이 사용됨

------------------------------------------------------------------------

# 실습하면서 느낀 점

처음에는 Controller에서 Service 객체를 직접 생성해 사용했지만, 이렇게
하면 메서드가 호출될 때마다 객체가 새로 만들어지는 문제가 있었다.

`@Autowired`를 이용해 스프링이 객체를 관리하도록 변경하니 객체를
재사용할 수 있었고, Controller는 요청 처리에만 집중하고 Service와
Repository는 각각 자신의 역할만 담당하는 구조가 되어 코드가 훨씬
깔끔해졌다.

이번 실습을 통해 **Spring이 객체를 관리하는 이유와 DI를 사용하는
목적**을 조금 더 이해할 수 있었다. 특히 생성자 주입이 현재 가장 권장되는
방식이라는 점도 익혔다.
